## Что такое H3-гексагоны

BrightBund использует библиотеку **Uber H3** (`github.com/uber/h3-go/v4`) для разбиения земной поверхности на шестиугольные ячейки (гексагоны). Каждая точка на карте (latitude, longitude) однозначно попадает в гексагон определённого разрешения.

Гексагоны выполняют роль **географических бакетов** — неизменных идентификаторов территорий, по которым группируются пользователи, задачи и рейтинги.

```go
// service.go:797-803
func computeH3Indices(lat, lon float64) (string, string, string) {
    latLng := h3.LatLng{Lat: lat, Lng: lon}
    cell5 := h3.LatLngToCell(latLng, h3ResDistrict)  // res5
    cell4 := h3.LatLngToCell(latLng, h3ResCity)       // res4
    cell2 := h3.LatLngToCell(latLng, h3ResCountry)    // res2
    return cell5.String(), cell4.String(), cell2.String()
}
```

## Три уровня разрешения

Система использует **три уровня H3-разрешения**, образующих иерархию от малого к большому:

| Константа        | Разрешение H3 | Охват           | Роль в системе              |
|------------------|---------------|------------------|-----------------------------|
| `h3ResDistrict`  | 5             | ~253 км² (19 км) | **Арена** — локальный лидерборд района |
| `h3ResCity`      | 4             | ~1 700 км² (59 км) | **Город** — лидерборд городского масштаба |
| `h3ResCountry`   | 2             | ~86 000 км² (607 км) | **Страна** — глобальные рейтинги и стабилизация |

```go
// service.go:20-23
const (
    h3ResCountry  = 2
    h3ResCity     = 4
    h3ResDistrict = 5
)
```

**Принцип вложенности**: Каждая задача и каждый пользователь получают **три гексагона одновременно**. Это позволяет вести рейтинги параллельно на трёх уровнях масштаба.

## Привязка к задачам и пользователям

### Задачи (Tasks)

При создании задачи (`CreateTask`) координаты задачи конвертируются в три H3-индекса:

- `h3_res5` — район, где расположена задача
- `h3_res4` — город
- `h3_res2` — страна

Эти индексы сохраняются в таблице `tasks` и индексируются для быстрого поиска. При выполнении задачи именно эти индексы определяют, **в какие лидерборды попадёт заработанный балл**.

### Пользователи (Users)

Пользователь получает свои H3-индексы при вызове `POST /api/v1/map/region`. Это определяет:
- В каком районе/городе пользователь «участвует»
- Видит ли он себя в локальном лидерборде
- Флаг `participate_district` — активное участие в районном рейтинге
- Флаг `location_opt_in` — согласие на геолокацию (можно отключить)

## Лидерборды

### Как формируется рейтинг

Когда помощник (helper) завершает задачу, система начисляет ему баллы и записывает их в **три параллельных лидерборда** на основе H3-гексагонов задачи:

```go
// service.go:765-785
func (s *Service) updateLeaderboards(userID string, task *Task) {
    year, week := now.ISOWeek()
    score := economy.CentinelsToSeals(task.Reward) // 1, 2 или 3 Silver Seals

    // 1. Арена (район) — res5
    key := "leaderboard:arena:{h3_res5}:week:{year}:{week}"
    s.recordLeaderboardScore(key, userID, score, now)

    // 2. Город — res4
    key := "leaderboard:city:{h3_res4}:week:{year}:{week}"
    s.recordLeaderboardScore(key, userID, score, now)

    // 3. Глобальный
    key := "leaderboard:global:week:{year}:{week}"
    s.recordLeaderboardScore(key, userID, score, now)
}
```

### Механика подсчёта

- **Хранилище**: Redis Sorted Sets (ZSET)
- **Операция**: `ZINCRBY` — инкрементальное добавление к текущему счёту пользователя
- **Изоляция по времени**: Каждый лидерборд привязан к **ISO-неделе** (`week:YYYY:WW`)
- **Изоляция по географии**: Каждый гексагон имеет свой отдельный лидерборд

### Формат ключей Redis

```
leaderboard:arena:{h3_res5_index}:week:{year}:{week}   -- Район
leaderboard:city:{h3_res4_index}:week:{year}:{week}    -- Город
leaderboard:global:week:{year}:{week}                   -- Глобальный
```

### Система баллов

Баллы = награда за задачу в **Silver Seals**. Допустимые значения: **1, 2 или 3** Silver Seals.

Внутри системы хранятся как **Centinels** (1 Seal = 100 Centinels), но в лидерборд записывается значение в Seals.

```go
var validRewards = map[int]bool{1: true, 2: true, 3: true}
```

### Пример

Пользователь выполнил задачу за 2 Silver Seals в Алматы. Его баллы добавляются в:
1. `leaderboard:arena:852a100704fffff:week:2026:14` (+2)
2. `leaderboard:city:842a10070ffffff:week:2026:14` (+2)
3. `leaderboard:global:week:2026:14` (+2)

Если он выполнит ещё одну задачу за 3 Seals в том же районе на той же неделе, его итоговый счёт в районном лидерборде станет **5**.

## Чемпион региона

Фоновый воркер (`worker.go`) каждый **час** сканирует все активные лидерборды и определяет **чемпиона** для каждого гексагона:

```go
// worker.go:92-96
func (w *Worker) snapshotChampions(ctx context.Context) {
    w.snapshotByPattern(ctx, "leaderboard:arena:*:week:*:*", 5)  // Районы
    w.snapshotByPattern(ctx, "leaderboard:city:*:week:*:*", 4)   // Города
    w.snapshotGlobalGoldChampion(ctx)                              // Глобальный
}
```

### Процесс определения чемпиона

1. **Сканирование Redis** — находит все лидерборды по паттерну
2. **Выборка лидера** — `ZRevRange(key, 0, 0)` — пользователь с максимальным счётом
3. **Разрешение ничьей** — если несколько пользователей с одинаковым счётом
4. **Сохранение** — запись в таблицу `region_champions` с обогащением гео-метаданными
5. **Отображение** — чемпионы появляются как маркеры (pins) на карте в мобильном приложении

### Глобальный чемпион

Отдельно определяется глобальный чемпион по **Gold Seals** (не Silver). Это чемпион с максимальным количеством заработанных Gold Seals за неделю. Записывается с `h3_index = "global"` и `resolution = 0`.

## Алгоритм Tie-Break

Когда несколько пользователей имеют **одинаковый максимальный счёт** в одном лидерборде, чемпион выбирается детерминистически:

### Уровень 1: Время первого вклада

Побеждает пользователь, который **первым** внёс вклад в текущий недельный лидерборд.

Для этого при каждом начислении баллов сохраняется timestamp:

```go
// service.go:791-794
firstSeenKey := leaderboardKey + ":first_seen"
_, _ = s.cache.HSetNX(ctx, firstSeenKey, userID, now.Unix())
```

`HSetNX` записывает только если ключа ещё нет — так фиксируется самый первый момент участия.

### Уровень 2: Дата создания аккаунта

Если timestamps совпадают или отсутствуют — побеждает пользователь с **самым старым аккаунтом** (`users.created_at`).

### Уровень 3: Лексикографический порядок

Последний fallback — **алфавитный порядок user_id** (наименьший ID выигрывает).

```
Приоритет: first_seen ASC → created_at ASC → user_id ASC
```

**Зачем**: Это гарантирует стабильный и предсказуемый результат для UX. Пользователь не будет «мерцать» как чемпион из-за нестабильности алгоритма.

## Стабилизация региона

### Проблема

Пользователь на границе двух районов (гексагонов res5) может при каждом обновлении GPS «прыгать» между соседними гексагонами. Это приводит к тому, что его баллы разбиваются между двумя лидербордами.

### Решение: Weekly Stabilization

```go
// service.go:692-712
func shouldKeepWeeklyRegion(prev *UserRegionState, nextRes5, nextRes4, nextRes2 string, now time.Time) bool {
    // Если страна изменилась → обновляем немедленно
    if prevRes2 != nextRes2 {
        return false
    }
    // Если та же ISO-неделя и та же страна → оставляем прежний район/город
    prevYear, prevWeek := prev.LocationUpdatedAt.UTC().ISOWeek()
    currYear, currWeek := now.UTC().ISOWeek()
    return prevYear == currYear && prevWeek == currWeek
}
```

### Правила

| Условие | Действие |
|---------|----------|
| Страна изменилась | Обновить все три гексагона немедленно |
| Та же страна, та же ISO-неделя | Оставить прежние res5 и res4 (район и город) |
| Та же страна, новая ISO-неделя | Обновить res5 и res4 по новым координатам |

Это гарантирует, что пользователь не «теряет» баллы в лидерборде района из-за GPS-дрейфа в пограничной зоне.

## Привязка к административным границам

Гексагоны не совпадают с административными границами (города, регионы, страны). Для привязки H3-ячейки к человеко-читаемому названию используется двухступенчатый алгоритм:

### Стратегия 1: Правило 50%+ перекрытия

```sql
-- Если более 50% площади гексагона попадает в административную границу,
-- гексагон считается принадлежащим этой территории.
overlap_ratio = ST_Area(ST_Intersection(boundary, h3_polygon))
              / ST_Area(h3_polygon)

-- При overlap >= 0.5 — назначается эта граница
```

**Разрешение ничьей при равном перекрытии**:
1. Наибольший `overlap_ratio`
2. Ближайший центроид границы к центроиду H3-ячейки
3. Алфавитный порядок имени границы
4. `boundary_id` по возрастанию

### Стратегия 2: Fallback по центральной точке

Если правило 50% не дало результата, используется центр гексагона:

```sql
SELECT city_name, region_name, country_name
FROM administrative_boundaries
WHERE ST_Covers(boundary, H3_CENTER_POINT)
```

### Кэширование

Результат сохраняется в таблице `h3_geo_metadata` — постоянный кэш, не требующий повторных расчётов.

## Связь с системой рангов

В BrightBund есть **две параллельные системы оценки**, и обе косвенно связаны с гексагонами:

### 1. Региональные чемпионы (Map Module) — еженедельно

| Параметр | Значение |
|----------|----------|
| Валюта | Silver Seals |
| Период | ISO-неделя (сброс каждую неделю) |
| Привязка | К гексагону задачи (res5, res4, global) |
| Результат | Чемпион района / города / мира |

### 2. Ранги (Ranks Module) — кумулятивно

| Параметр | Значение |
|----------|----------|
| Валюта | Gold Seals |
| Период | Всё время (накопительный) |
| Привязка | К пользователю (без географии) |
| Результат | Ранг от Pearl до Supernova |

**Каталог рангов** (определяется по кумулятивным Gold Seals):

| Ранг | Gold Seals | Качество | Уровни |
|------|-----------|----------|--------|
| Pearl | 0–10 | Origin | C, B, A, S |
| Moonstone | 10–30 | Clarity | C, B, A, S |
| Jade | 30–70 | Integrity | C, B, A, S |
| Lapis Lazuli | 70–170 | Ascendance | C, B, A, S |
| Ammolite | 170–300 | Fortitude | C, B, A, S |
| Onyx | 300–1000 | Transcendence | C, B, A, S |
| Supernova | 1000+ | Sovereign | C, B, A, S |

**Ключевое различие**: Гексагоны влияют на **региональных чемпионов** (еженедельная конкуренция внутри географической зоны), но **не на ранги** (ранги — глобальная кумулятивная метрика).

## FAQ: Подробные ответы на вопросы о гексагонах и рейтингах

### 1. Как именно определяется принадлежность гексагона к стране, региону и городу?

Принадлежность определяется функцией `ResolveH3ToLocation()` ([service.go:843-894](service.go#L843-L894)), которая работает в три этапа:

1. **Проверка кэша** — ищется запись в таблице `h3_geo_metadata` по H3-индексу. Если найдена — возвращается сразу.
2. **Правило 50%+ перекрытия** — строится полный полигон гексагона (`boundaryWKTOfH3`), и SQL-запрос считает долю пересечения с каждой административной границей (страна level=0, регион level=1, город level=2). Граница с перекрытием >= 50% считается «владельцем» гексагона.
3. **Fallback по центральной точке** — если полигонный метод не дал результата, берётся центр гексагона (`centerOfH3`) и ищется `ST_Covers`/`ST_Within` по административным границам.

Результат сохраняется в кэш для последующих запросов.

### 2. Используется ли сам полигон гексагона или только его центральная точка?

**Оба варианта**, в приоритетном порядке:

- **Приоритет 1**: Полный полигон гексагона. Функция `boundaryWKTOfH3()` ([service.go:907-926](service.go#L907-L926)) строит WKT-полигон из всех вершин H3-ячейки и передаёт его в PostGIS-запрос `GetAdministrativeHierarchyByHex()`.
- **Приоритет 2 (fallback)**: Центральная точка. Используется, только если полигонный метод вернул пустой результат (нет границы с 50%+ перекрытием). Функция `centerOfH3()` ([service.go:896-905](service.go#L896-L905)) вычисляет центр ячейки.

Таким образом, в нормальных условиях система работает с **полным полигоном**, а центральная точка — это защитный fallback.

### 3. Что происходит, если гексагон попадает на границу двух или более стран/регионов?

Система применяет **детерминистический алгоритм разрешения конфликтов** в SQL-запросе `GetAdministrativeHierarchyByHex()` ([repository.go:611-666](repository.go#L611-L666)):

```sql
ORDER BY overlap_ratio DESC,           -- 1) максимальная доля перекрытия
         centroid_distance_meters ASC,  -- 2) ближайший центроид границы к центроиду гексагона
         name ASC,                      -- 3) алфавитный порядок имени границы
         id ASC                         -- 4) стабильный ID границы в БД
```

**Правила по уровням**:
- Для каждого уровня (страна, регион, город) выбирается **одна** граница с наибольшим перекрытием (>= 50%)
- Если две границы имеют одинаковый процент перекрытия — побеждает та, чей центроид ближе к центру гексагона
- Если и это совпадает — алфавитный порядок названия, затем ID

**Важно**: Фильтр `WHERE overlap_ratio >= 0.5` означает, что гексагон должен покрываться хотя бы на 50%. Если ни одна граница не покрывает 50%, полигонный метод не даёт результата, и срабатывает fallback по центральной точке.

### 4. Это правило всегда одинаковое и стабильное?

**Да, правило полностью детерминистическое.** Для одного и того же набора данных (гексагон + административные границы) результат всегда будет одинаковым, потому что:

- SQL-запрос использует `ROW_NUMBER()` с полным порядком сортировки (4 критерия), исключающим неоднозначность
- Tie-break доходит до `id ASC` — уникального идентификатора границы в БД, что гарантирует единственный результат
- Нет случайных или временнЫх компонентов в алгоритме

Единственный случай, когда результат может измениться — это обновление данных в таблице `administrative_boundaries` (например, импорт новых границ из OSM).

### 5. Если один и тот же гексагон определяется сегодня и завтра — будет ли результат одинаковым?

**Да**, при условии что данные в `administrative_boundaries` не менялись. Более того:

- После первого определения результат **кэшируется** в таблице `h3_geo_metadata` ([repository.go:678-691](repository.go#L678-L691))
- При повторном запросе система вернёт кэшированный результат, не пересчитывая
- Кэш обновляется через `ON CONFLICT DO UPDATE`, то есть при пересчёте старое значение перезаписывается

Риск «прыгания» возможен **только** если:
- Обновились данные административных границ (новый импорт OSM)
- Кэш был намеренно очищен и произошёл пересчёт с новыми данными

### 6. Как система ведёт себя в спорных зонах?

**Трёхуровневая fallback-логика** ([service.go:843-894](service.go#L843-L894)):

| Этап | Метод | Когда применяется |
|------|-------|-------------------|
| 1 | Кэш (`h3_geo_metadata`) | Гексагон уже был определён ранее |
| 2 | Полигон 50%+ (`GetAdministrativeHierarchyByHex`) | Первое определение; есть границы с >= 50% перекрытием |
| 3 | Центральная точка (`GetAdministrativeHierarchy`) | Полигонный метод не дал результата (ни одна граница не покрывает 50%) |

**Для сложных случаев:**
- **Узкие участки**: Если гексагон пересекает много мелких границ, но ни одна не покрывает 50% — сработает fallback по центральной точке, что даёт стабильный результат
- **Границы между странами**: 4-уровневый tie-break в SQL гарантирует единственный выбор
- **Сложные полигоны (анклавы, эксклавы)**: PostGIS корректно обрабатывает `ST_Intersection` для любых валидных геометрий

### 7. Что происходит, если система не может определить принадлежность?

Есть **явная защита от nil-ошибок** ([service.go:871-884](service.go#L871-L884)):

```go
// SAFETY GUARD: If metadata is still nil after both lookups
if metadata == nil {
    metadata = &H3GeoMetadata{
        H3Index:     h3Index,
        CityName:    "",
        RegionName:  "",
        CountryName: "",
        CountryCode: "",
    }
}
```

Если оба метода (полигон и центральная точка) не дали результата:
- Возвращается **пустой объект** с пустыми строками вместо названий
- Система **не падает** — нет panic/nil pointer dereference
- Пустой результат кэшируется в `h3_geo_metadata` (чтобы не пересчитывать)
- Чемпион для такого гексагона будет записан без гео-метаданных (поля city/region/country останутся пустыми)

### 8. Используется ли кэширование?

**Да.** Кэширование реализовано на уровне PostgreSQL-таблицы `h3_geo_metadata`:

```go
// service.go:843-851 — проверка кэша
metadata, err := s.repo.GetH3GeoMetadata(ctx, h3Index)
if metadata != nil {
    return metadata, nil  // кэш найден — возвращаем без пересчёта
}

// service.go:889-891 — запись в кэш
if err := s.repo.UpsertH3GeoMetadata(ctx, metadata); err != nil {
    return nil, err
}
```

**Порядок**: кэш → полигон 50% → центральная точка → запись в кэш.

### 9. Где хранится кэш и как долго живёт?

| Параметр | Значение |
|----------|----------|
| **Хранилище** | PostgreSQL, таблица `h3_geo_metadata` |
| **Primary Key** | `h3_index` (VARCHAR(20)) |
| **Поля** | `city_name`, `region_name`, `country_name`, `country_code`, `resolved_at` |
| **TTL** | **Бессрочный** (перманентный кэш) |
| **Обновление** | `INSERT ... ON CONFLICT DO UPDATE` — при повторном определении старая запись перезаписывается с новым `resolved_at = NOW()` |

Это **материализованный кэш**: один раз определённый гексагон больше не требует пространственных вычислений. При необходимости TTL можно добавить на уровне приложения (сейчас не реализовано).

### 10. Будет ли нагрузка расти при большом количестве пользователей?

**Нагрузка на геолокацию минимальна** благодаря архитектуре:

- **H3-вычисления** (`computeH3Indices`) — это **чистая математика** на стороне Go, без обращения к БД. Вычисление трёх гексагонов занимает микросекунды.
- **Пространственные запросы** (PostGIS) выполняются **только при первом определении** нового гексагона. После этого результат кэшируется навсегда.
- **Количество уникальных гексагонов конечно**: на res5 (~253 км²) вся Земля покрыта ~150 тыс. ячейками. Реально активных будет на порядки меньше. Кэш `h3_geo_metadata` быстро «прогреется» и пространственные запросы перестанут вызываться.
- **Лидерборды** в Redis — операция `ZINCRBY` имеет сложность O(log N), где N — количество пользователей в гексагоне.

**Узкое место**: Потенциально — `SCAN` по Redis-ключам в воркере `snapshotChampions`, который каждый час ищет `leaderboard:arena:*:week:*:*`. При очень большом количестве активных гексагонов можно перейти на реестр активных лидербордов.

### 11. Есть ли риск, что логика станет узким местом при масштабировании?

**Маловероятно для текущей архитектуры**, но есть потенциальные точки роста:

| Компонент | Сложность | Риск при масштабировании |
|-----------|-----------|-------------------------|
| `computeH3Indices()` | O(1), in-memory | Нет риска |
| Кэш `h3_geo_metadata` | O(1) по PK | Нет риска |
| PostGIS 50%+ overlap | O(N) по границам, пространственный индекс | Низкий (GiST индекс) |
| Redis `ZINCRBY` | O(log N) | Низкий |
| Worker `SCAN` | O(K) по количеству лидербордов | **Средний** при миллионах активных гексагонов |
| `pickChampionUserID` | O(M) по числу tied users | Низкий |

**Рекомендации на будущее**:
- Заменить `SCAN` на явный реестр активных лидербордов
- Добавить пагинацию в воркер снимков
- Рассмотреть шардирование Redis по регионам

### 12. Как система масштабируется на разные страны?

H3 — это **равномерная** система: гексагоны одного разрешения имеют примерно одинаковую площадь по всей Земле (с небольшими вариациями из-за проекции). Это означает:

| Страна | Размер res2 (~86k км²) | Количество res5 внутри | Эффект |
|--------|----------------------|----------------------|--------|
| Казахстан (2.7M км²) | ~31 гексагон | ~10 700 районов | Много мелких арен |
| Люксембург (2.5k км²) | Попадает в 1 гексагон | ~10 районов | Мало арен, но каждая с полноценным лидербордом |

**Потенциальный перекос**: В маленькой стране может быть всего несколько районных лидербордов с высокой конкуренцией, а в большой стране — тысячи лидербордов с 1-2 участниками каждый. Это **не баг, а особенность** H3-подхода: рейтинги привязаны к площади, а не к населению.

**Сейчас нет** механизма динамической подстройки разрешения по плотности населения (упомянуто как «Future Enhancement» в GEO_CONFIG.md).

### 13. Как определяется «район» внутри города?

**Район = гексагон res5.** Это **не** реальные административные границы внутри города, а фиксированные гексагональные ячейки площадью ~253 км² (диаметр ~19 км).

- Таблица `administrative_boundaries` используется только для **именования** (город, регион, страна), а не для деления на районы
- Внутри города деление происходит **исключительно по H3-сетке** — каждый гексагон res5 = отдельный «район» (arena)
- В системе нет привязки к реальным административным районам (например, Алмалинский район, Бостандыкский район)

### 14. Что если город очень маленький?

Маленький город (например, ~50 км²) полностью попадёт в **один** гексагон res5 (~253 км²). Это означает:

- У города будет **один районный лидерборд** (одна арена)
- Все пользователи города конкурируют в одном рейтинге
- Городской лидерборд (res4, ~1700 км²) и районный будут фактически идентичны по составу участников

Система **не делит** маленький город на более мелкие части — разрешение H3 фиксировано на res5.

### 15. Что если город очень большой?

Большой город (например, Алматы — ~680 км²) будет покрыт **несколькими** гексагонами res5:

- Алматы ≈ 2-3 гексагона res5
- Москва (~2500 км²) ≈ 8-10 гексагонов res5
- Каждый гексагон = отдельная арена со своим лидербордом

**Деление происходит исключительно по H3-сетке**, без привязки к реальным административным районам. Границы арен — это границы гексагонов, которые не совпадают с границами реальных районов города.

### 16. Может ли маленький город считаться «районом», а большой район — тем же уровнем?

**Да, это возможно и ожидаемо.** Все «районы» (арены) — это гексагоны одного разрешения (res5, ~253 км²), независимо от реального содержимого:

- Маленький город в Европе (~20 км²) = часть одной арены
- Промышленный район Казахстана (~300 км²) = 1-2 арены

Система **не различает** городские и негородские гексагоны. Лидерборд арены — это лидерборд **территории**, а не административной единицы.

### 17. Есть ли единая иерархия страна → регион → город → район?

**Частично.** Иерархия существует, но на разных уровнях работает по-разному:

| Уровень | Источник | Метод определения |
|---------|----------|-------------------|
| Страна (res2) | `administrative_boundaries` level=0 | 50%+ перекрытие / центральная точка |
| Регион (res4) | `administrative_boundaries` level=1 | 50%+ перекрытие / центральная точка |
| Город (res4) | `administrative_boundaries` level=2 | 50%+ перекрытие / центральная точка |
| Район/Арена (res5) | **H3-сетка** | Чистая математика, без адм. границ |

**Где может «ломаться»**:
- Город и регион используют один и тот же уровень H3 (res4), но разные уровни административных границ
- Район (арена) вообще не привязан к административным данным — это чисто гексагональная единица
- Если в `administrative_boundaries` нет данных для какого-то уровня (например, нет level=2 для городов), то поле `city_name` будет пустым

### 18. Что если административные данные неточные или неполные?

Система имеет **многоуровневую защиту**:

1. **Fallback по центральной точке** — если полигонный метод не дал результата из-за неточных границ, центральная точка часто попадает корректно
2. **Safety guard** ([service.go:871-884](service.go#L871-L884)) — если оба метода не дали результата, возвращается пустой объект (не crash)
3. **Кэш перезаписывается** — если данные обновятся, при следующем вызове `ResolveH3ToLocation` с force-пересчётом кэш обновится
4. **Лидерборды работают независимо от названий** — даже без корректных гео-названий, лидерборды по H3-индексам работают исправно (ключ Redis — это H3-индекс, а не название города)

**Что пострадает**: Только отображение названий в UI (вместо «Алматы» может быть пустая строка). Рейтинги и баллы **не пострадают**.

### 19. Как система ведёт себя при смене локации пользователем?

При каждом вызове `POST /api/v1/map/region` ([service.go:635-690](service.go#L635-L690)):

1. Вычисляются новые H3-индексы по координатам
2. Проверяется **правило еженедельной стабилизации** (`shouldKeepWeeklyRegion`)
3. Если та же ISO-неделя и та же страна — **район и город не меняются**
4. Если другая страна или новая неделя — обновляются все три уровня
5. Обновляется `location_updated_at = NOW()`

**Ограничений по частоте вызовов** эндпоинта `/map/region` **нет** (нет rate-limit или throttle на уровне модуля map). Однако благодаря weekly stabilization, частые вызовы в рамках одной недели не приводят к смене района.

### 20. Может ли пользователь «прыгать» между гексагонами?

**В рамках одной ISO-недели — нет** (при условии, что страна не менялась). Механизм `shouldKeepWeeklyRegion()` ([service.go:692-712](service.go#L692-L712)) фиксирует район и город на всю неделю:

```go
// Если GPS показывает другой район, но та же страна и та же неделя:
if prevRes2 == nextRes2 && sameISOWeek {
    // Оставляем прежние res5 и res4
    h3Res5 = prev.H3Res5
    h3Res4 = prev.H3Res4
}
```

**Между неделями — да**, район может измениться. Это нормальное поведение: с новой недели начинается новый лидерборд, и пользователь получает актуальный район.

**Исключение**: Если страна изменилась (например, пользователь переехал из KZ в RU) — район обновляется **немедленно**, даже в рамках одной недели.

### 21. Есть ли защита от злоупотреблений геолокацией?

**Текущие защиты**:

| Механизм | Описание |
|----------|----------|
| Weekly stabilization | Район фиксируется на неделю — нельзя «прыгать» для сбора баллов в разных лидербордах |
| `location_opt_in` | Пользователь может отключить геолокацию |
| `participate_district` | Отдельный флаг участия в районном рейтинге |
| Баллы привязаны к задаче | Баллы идут в лидерборд гексагона **задачи**, а не **пользователя** |

**Чего нет**:
- Нет rate-limit на вызовы `/map/region`
- Нет верификации координат (GPS spoofing не детектируется)
- Нет проверки реалистичности перемещения (например, нельзя быть в Алматы и через минуту в Москве)
- Нет привязки координат к IP-адресу

**Важный нюанс**: Баллы записываются в лидерборд на основе координат **задачи**, а не пользователя. То есть даже если пользователь подменит свою локацию, баллы всё равно попадут в гексагон, где была создана задача.

### 22. Как определяется окончательная зона для рейтинга?

**Зона определяется немедленно и автоматически**, без подтверждения:

- **Для задачи**: При создании (`CreateTask`) H3-индексы вычисляются из координат задачи и сохраняются. Эти индексы **неизменны** после создания — лидерборд задачи всегда привязан к месту её создания.
- **Для пользователя**: При вызове `SetUserRegion` H3-индексы обновляются (с учётом weekly stabilization). Это влияет на отображение в UI, но **не на лидерборды** — лидерборды привязаны к задачам.

Фактически, **окончательная зона для рейтинга = гексагон задачи**, который фиксируется в момент создания задачи и никогда не меняется.

### 23. Есть ли риск, что при обновлениях логики старые гексагоны начнут определяться иначе?

**Есть два уровня риска**:

**Уровень 1 — H3-индексы (LOW RISK)**:
- H3-индексы детерминистичны: одна и та же координата всегда даёт один и тот же индекс на заданном разрешении
- Библиотека `uber/h3-go` следует спецификации H3, которая стабильна между версиями
- Риск: обновление major-версии H3 теоретически может изменить маппинг (крайне маловероятно)

**Уровень 2 — Гео-названия (MEDIUM RISK)**:
- Если обновятся данные в `administrative_boundaries` (новый импорт OSM), гексагоны на границах могут получить другие названия
- Кэш `h3_geo_metadata` перезапишется при следующем вызове `ResolveH3ToLocation`
- **Старые записи в `region_champions`** хранят названия на момент записи и **не обновляются** ретроактивно

**Уровень 3 — Лидерборды (NO RISK)**:
- Redis-ключи используют H3-индексы, а не названия. Даже если название гексагона изменится, лидерборд остаётся тем же
- `region_champions` привязаны к `h3_index`, а не к названию

**Защита**: Можно добавить версионирование в `h3_geo_metadata` для отслеживания изменений названий.
