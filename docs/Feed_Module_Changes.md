## 1. Фикс Anti-Doomscroll: мульти-устройственный таймер перерыва

### Суть проблемы

Пользователь листал ленту с телефона, набрал лимит (например, 30 минут), система поставила его на 5-минутный перерыв. Если в этот момент он открывал приложение с другого устройства — таймер перерыва сбрасывался. Flutter на первом устройстве думал, что перерыв ещё идёт, а сервер уже позволял листать.

### Решение (реализовано)

- Таймер перерыва теперь строго привязан к `break_start_at` (wall-clock anchor). Все устройства вычисляют оставшееся время одинаково: `break_duration - (now - break_start_at)`.
- Сервер возвращает корректные значения `break_seconds_remaining` и `action_required` для всех сценариев ("trigger_friction", "enforce_cooldown", или отсутствие поля).
- Все переходы состояния и расчёты времени теперь полностью соответствуют спецификации: break не сбрасывается при открытии с другого устройства, и всегда синхронизирован между всеми клиентами.
- Вся логика реализована без изменений в API-контрактах или полях ответа.

### Ответ `GET /api/v1/feed/state` и `POST /api/v1/feed/sync`

```json
{
  "accumulated_active_seconds": 1800,
  "is_in_cooldown": true,
  "break_seconds_remaining": 187,
  "accumulated_break_seconds": 113,
  "max_allowed_seconds": 1800,
  "server_timestamp": "2026-03-09T14:22:00.000Z",
  "action_required": "enforce_cooldown"
}
```

### Важно для Flutter

| Значение `action_required` | Что делать |
|---|---|
| `"trigger_friction"` | Показать friction-экран (прогресс-бар заполнился) |
| `"enforce_cooldown"` | Пользователь уже в перерыве — показать экран блокировки |
| _(отсутствует)_ | Обычный режим |

- `break_seconds_remaining` — сколько осталось до конца перерыва, считать countdown с этого значения
- **Friction percent** вычислять только из ответа сервера: `accumulated_active_seconds / max_allowed_seconds`, **никогда не хранить локально**
- При открытии приложения на любом устройстве — вызвать `GET /feed/state`, получить актуальное состояние. Оба устройства увидят одно и то же

## 2. Новые эндпоинты: посты на профиле

**Реализовано полностью.** Все четыре маршрута работают, соответствуют спецификации и не требуют изменений на стороне клиента.

- `GET /api/v1/profiles/me/posts` — возвращает сетку постов пользователя с поддержкой пагинации, лимитов (по умолчанию 18, максимум 30), и корректной генерацией `next_cursor`.
- `GET /api/v1/profiles/:user_id/posts` — возвращает сетку постов другого пользователя с фильтрацией по видимости (self/ally/stranger).
- `GET /api/v1/profiles/me/posts/list` — возвращает ленту постов пользователя (полные карточки), поддерживает `anchor_post_id` (включительно, через created_at+1µs), корректно обрабатывает fallback на cursor, лимиты (по умолчанию 10, максимум 30), и next_cursor.
- `GET /api/v1/profiles/:user_id/posts/list` — аналогично, но для другого пользователя, с фильтрацией по видимости.

**Проверено тестами:**
- Лимиты (default/max) и пагинация покрыты unit-тестами.
- Anchor fallback и cursor-логика протестированы.
- Контракты и поля ответа не менялись.

```
1. Открыл профиль
   └── GET /profiles/me/posts?limit=18

4. Прокрутил вниз в списке
   └── GET /profiles/me/posts/list?cursor={next_cursor}&limit=10
       → подгрузить следующие посты
```

## 3. Фикс worker'а — надёжность хранения данных

**Реализовано полностью.** Все три функции worker'а теперь работают, покрыты тестами на retry/requeue, и гарантируют отсутствие потерь данных при сбоях Postgres.

- `flushFatigueStates` — каждые 30 сек читает dirty пользователей из Redis и делает UPSERT в feed_fatigue_states. При ошибке пользователь возвращается в очередь.
- `flushLikes` — лайки из Redis сбрасываются батчем в post_interactions и обновляют likes_count. При ошибке лайки и post_id возвращаются в очередь.
- `flushSeals` — атомарно забирает счётчики силов из Redis и обновляет seals_count/seals_amount в posts. При ошибке значения возвращаются в очередь.

**Покрытие тестами:**
- Все retry/requeue сценарии протестированы через miniredis и unit-тесты.
- Контракты и структура очередей не менялись.

## 4. Модерация и качество ленты: консистентная санкционная лестница (реализовано)

### Что изменено в серверной логике (без изменений API)

- Нормализовано решение модерации: `accepted` теперь интерпретируется как `actioned` на сервере, чтобы не терялись санкции и страйки.
- Авторские страйки стали типизированными по цели: `post_removed` и `comment_removed` (с поддержкой legacy `content_violation` в чтении).
- Ограничение публикации (`publishing_restricted`) теперь считается по активным страйкам автора за 30 дней, с лестницей:
  - 3+ страйка → блок публикации до 24 часов от последнего страйка
  - 6+ страйков → до 72 часов
  - 9+ страйков → до 7 дней
- На ранжирование smart-feed теперь влияют все контентные страйки автора (`post_removed`, `comment_removed`, `content_violation`), что устраняет рассинхрон write/read логики.

### Качество выдачи при низком объёме данных

- В smart blending добавлен «предпочитаемый» лимит повторов по автору (до 2 постов на автора на первом проходе).
- Если кандидатов мало, система автоматически делает backfill без этого лимита, чтобы не терять наполнение страницы.
- Результат: выше разнообразие ленты при малом пуле постов, без изменения контрактов и формата ответа.
- Для стабильной пагинации при одинаковом `created_at` добавлен детерминированный tie-break в SQL сортировке: `ORDER BY created_at DESC, id DESC`.

### Фиксированные параметры адаптивной geo-логики ленты

Параметры задаются централизованно в конфиге backend (`backend/config.yaml`, `backend/config.local.yaml`, секция `feed`) и применяются в модуле ленты без изменения API/алгоритма.

- В модуле ленты используется ring-модель эквивалентного охвата: **kRing 1 → 2 → 3** через фиксированные радиусы.
- Радиусы локальной зоны:
  - `kRing=1` → **5 км**
  - `kRing=2` → **10 км**
  - `kRing=3` → **18 км**
- Окно оценки локальной активности: **последние 24 часа**
- Порог «достаточной локальной активности»:
  - минимум **30 локальных постов / 24ч**
  - минимум **15 уникальных локальных авторов / 24ч**
- Порог «средней локальной активности»:
  - минимум **15 постов / 24ч**
  - минимум **8 авторов / 24ч**
- Доли локального контента:
  - низкая активность: **30% локального**
  - средняя активность: **50% локального**
  - высокая активность: **70% локального**

Ключи конфига:

- `feed.adaptive_geo_enabled`
- `feed.max_k_ring`
- `feed.ring1_radius_km`, `feed.ring2_radius_km`, `feed.ring3_radius_km`
- `feed.min_local_posts_24h`, `feed.min_local_authors_24h`
- `feed.med_local_posts_24h`, `feed.med_local_authors_24h`
- `feed.local_share_low`, `feed.local_share_medium`, `feed.local_share_high`

### Как выбирается локальная зона

1. Для текущей позиции пользователя берётся точка `lat/lon`.
2. Строятся эквивалентные кольца локальности `kRing=1..3` как фиксированные радиусы (5/10/18 км).
3. Для каждого кольца считается локальная активность за 24ч (посты + уникальные авторы).
4. Берётся минимальное кольцо, которое проходит порог достаточной активности; если ни одно не проходит — используется `kRing=3`.
5. По уровню активности выбранного кольца назначается доля локального контента (30/50/70).

### Где код гексов

- Код расчёта H3-гексов (res2/res4/res5) и назначения региона пользователя находится в map-модуле:
  - `backend/internal/modules/map/service.go` (`computeH3Indices`, `SetUserRegion`)
  - `backend/internal/modules/map/repository.go` (`UpdateUserRegion`, `GetRegionChampions`)

## Общее описание Feed-модуля

### Что такое Feed-модуль

Feed-модуль отвечает за всё, что связано с лентой контента в приложении: публикацию постов, комментарии, лайки, силы (seals), умную ленту с геолокацией, а также за систему Anti-Doomscroll — ограничение времени, проведённого в ленте.

---

### Архитектура хранения данных

Модуль использует два уровня хранения:

| Слой | Технология | Назначение |
|---|---|---|
| Кэш (первичный) | Redis | Быстрые операции: счётчики лайков, силов, состояние усталости пользователя |
| Персистентное хранилище | PostgreSQL | Долгосрочное хранение всех данных |

Фоновый worker каждые **30 секунд** синхронизирует «грязные» данные из Redis в Postgres. Это позволяет не нагружать базу данных на каждый лайк или тик ленты.

---

### Anti-Doomscroll — система ограничения времени

Цель системы — мягко ограничить время пользователя в ленте и заставить сделать перерыв.

#### Константы системы

| Константа | Значение | Описание |
|---|---|---|
| `DefaultMaxAllowedActiveSeconds` | 1200 сек (20 мин) | Лимит по умолчанию, если у пользователя не задан |
| `BreakDurationSeconds` | 300 сек (5 мин) | Длина обязательного перерыва |
| `AwayResetThreshold` | 300 сек (5 мин) | Если пользователь отсутствовал в ленте дольше этого — счётчик времени сбрасывается |
| `NetworkBufferSeconds` | 5 сек | Погрешность для защиты от читерства с часами |

Пользовательский лимит хранится в колонке `feed_time_limit_mins` таблицы `users`. Допустимые значения: `0` (без лимита), `20`, `30`, `40` минут.

#### Конечный автомат состояний

```
[ACTIVE] ──── достиг лимита ────► [COOLDOWN]
   ▲                                   │
   │                                   │ отсутствовал ≥ BreakDurationSeconds
   │                                   │ (вычисляется через break_start_at)
   └──────────── сброс ◄───────────────┘

[ACTIVE] ──── отсутствовал ≥ AwayResetThreshold (5 мин) ────► сброс счётчика → [ACTIVE с 0]
```

#### Два вызова, которые использует Flutter

| Эндпоинт | Когда вызывать | Что делает |
|---|---|---|
| `GET /api/v1/feed/state` | При открытии/возврате в ленту | Применяет переходы состояния (считает off-feed время как время перерыва) |
| `POST /api/v1/feed/state/sync` | Периодически пока пользователь в ленте | Накапливает активное время, возвращает актуальный статус |

`SyncFeedState` принимает тело:
```json
{ "delta_seconds": 15 }
```

Сервер проверяет дельту через anti-cheat: если `delta_seconds > реальное_прошедшее_время + 5сек` — значение обрезается. Это защита от клиентских манипуляций.

### Посты и лента

#### Создание поста — `POST /api/v1/posts`

```json
{
  "caption": "Текст поста",
  "visibility": "ANYONE",
  "comment_permission": "ANYONE",
  "media_attachments": [
    { "type": "image", "url": "https://...", "thumbnail_url": "https://..." }
  ]
}
```

`visibility`: `ANYONE` | `ALLIES_ONLY`

`comment_permission`: `ANYONE` | `ALLIES_ONLY` | `NO_ONE`

#### Умная лента — `GET /api/v1/feed`

Лента формируется на основе геолокации пользователя (радиус поиска постов), союзников и времени публикации. Пагинация — по курсору (`created_at` в формате RFC3339Nano).

Query params: `lat`, `lon`, `cursor`, `limit` (по умолчанию 10).

---

### Комментарии

Комментарии поддерживают древовидную структуру (треды). Каждый комментарий может иметь `parent_id` — ссылку на родительский комментарий.

| Эндпоинт | Описание |
|---|---|
| `POST /api/v1/posts/:post_id/comments` | Создать комментарий или ответ |
| `GET /api/v1/posts/:post_id/comments` | Получить корневые комментарии |
| `GET /api/v1/posts/:post_id/comments?parent_id=uuid` | Получить ответы на конкретный комментарий |

---

### Лайки

Лайк — это toggle: первый запрос ставит лайк, повторный — снимает.

`POST /api/v1/posts/:post_id/likes`

Лайк записывается в Redis (буфер), worker сбрасывает накопленные лайки батчем в `post_interactions` и обновляет `likes_count` в таблице `posts`.

`viewer_has_liked` в карточке поста показывает актуальное состояние для текущего пользователя.

---

### Силы (Seals)

Seals — это монетизированная реакция: пользователь отправляет другому пользователю виртуальную валюту  на пост.

`POST /api/v1/posts/:post_id/seals`

```json
{ "amount": 100, "comment": "Отличный пост!" }
```

Логика:
1. Экономический модуль списывает  со счёта отправителя
2. Начисляет получателю
3. Счётчики `seals_count` и `seals_amount` на посте обновляются через Redis → worker → Postgres

`GET /api/v1/posts/:post_id/seals` — список тех, кто отправил силы на пост (с суммами и комментариями).

---

### Хранилище состояния: таблица `feed_fatigue_states`

```
user_id                    UUID (PK)
accumulated_active_seconds INTEGER   — сколько секунд пользователь провёл в ленте
accumulated_break_seconds  INTEGER   — сколько секунд перерыва уже прошло
last_sync_timestamp        TIMESTAMP — время последнего sync-запроса
is_in_cooldown             BOOLEAN   — находится ли в режиме перерыва
break_start_at             TIMESTAMP — якорная точка начала перерыва (неизменяема)
```

Одна строка на пользователя. Все устройства читают одну и ту же строку — кросс-девайс синхронизация гарантирована.
